Durable Agent Runtime

plain while 플래너와 중앙 Orchestrator 실행 경계의 실제 노드·엣지 구조도. 권한은 실행 전 pre_tool_use에서만 결정되고, batch는 이벤트나 control point가 아닌 실행 최적화 단위로만 존재한다.

01 · System flow

전체 런타임 구조

모델은 effect를 요청할 뿐 실행하지 않는다. 모든 tool effect는 Orchestrator의 pending 기록, 호출별 권한 게이트, StepLog를 거쳐 외부 세계에 도달한다. tool 결과는 정상 경로에서 durable inbox를 거치지 않는다 — 같은 라운드 안의 carried input이고, inbox를 통과하는 건 복구가 복원해 넣을 때다.

02 · Approval

실행 전 승인과 worker 없는 재개

PermissionRequest 이벤트가 권한을 결정하지 않는다. awaited pre_tool_use가 Suspend를 반환하고, Orchestrator가 continuation을 저장한 뒤 attempt를 종료한다.

03 · Control plane

Control, Signal, Event는 서로 다른 채널이다

같은 lifecycle 시점을 공유해도 운반하는 의미가 다르다. 결정은 typed return, 외부 답은 durable input, 이벤트는 감사 가능한 observation이다.

amber 는 BLOCKING에 등재된 이벤트다. 결정 지점을 알리는 이벤트이고, 실제 결정은 짝지어진 control point가 한다 — UserPromptSubmit → on_inputs, PreToolUse → pre_tool_use, PermissionRequest → on_resume. 나머지는 전부 결과 통지다. 짝이 없는 이벤트는 등재하지 않는다: PreCompact와 Elicitation은 대응 control point가 생기는 날 함께 돌아온다.

Batch 전용 이벤트와 control point는 없다. 여러 호출은 각각 PreToolUse → PostToolUse/PostToolUseFailure를 가진다. call order는 pending round와 StepLog가 보존하고, 동시성은 Concurrent가 모든 호출의 is_concurrency_safe 선언을 보고 결정한다.
이벤트 채널은 감사 기록이 아니다. 싱크 실패는 로그 후 스킵이고 재전송이 없다 — at-most-once다. event_id는 한 스트림 안의 재발행(복구가 복원한 tool 결과를 다시 알리는 경우)을 알아보는 용도이며, sequence가 좌표에 들어가고 새 EventStream에서 0부터 시작하므로 프로세스를 건너뛰는 키가 아니다. 잃으면 안 되는 기록은 after_tool_call에 쓴다 — raise가 그대로 올라가 run을 멈춘다.
control stage는 재실행된다. tool 경계 둘은 ledger에서 다시 불리고(recover_pending이 복원한 결과에도 after_tool_call을 다시 부른다), 나머지는 라운드가 다시 돌아서 다시 불린다. 누적 카운터와 비멱등 외부 쓰기를 stage에 두면 이중 계산된다. durable 사본을 바꿔야 하면 stage가 아니라 Tools 래퍼를 쓴다 — orchestrator가 Concurrent(Stepped(tools))로 감싸므로 사용자 executor가 step 안쪽이다.
04 · Recovery

Effect 상태와 복구 결정

graph program counter 대신 호출별 effect 상태를 읽는다. 완료 결과는 재사용하고, 실행 중 장애창은 정확히 모른다고 표시하며, 승인 대기는 worker 없이 continuation으로 남는다. 거부는 ledger에 남기지 않는다 — 거부도 답변이고, 답변된 호출은 애초에 pending이 아니다. 결과로 기록하면 실행된 적 없는 effect가 완료 step으로 재생된다.
